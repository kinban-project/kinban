# シフト・勤怠 業務受入テスト 最終報告

実施日: 2026-07-19  
対象: ローカル開発環境、ローカルD1、Browser / API / MCP  
判定: **小規模での基本フローは動くが、現状のまま100人規模や勤怠確定業務へ投入するのは非推奨**

## 結論

グループ作成、参加承認、勤務希望、シフト公開、出退勤、日次申告、月次の差戻し・承認という主要フローはAPI経由で完走した。一般メンバーによる他人の勤怠取得・承認、非所属グループへのアクセスも拒否された。

一方、評価メモの漏えい、同時出勤による重複勤怠、未来シフトへの即時打刻、日次未提出のまま月次承認、同時シフト更新の上書き消失がある。これらは給与・勤務実績・評価情報の信頼性に直結するため、先に修正すべきである。

MCPは単なる別操作経路ではなく、Browser/APIと異なる業務状態を作る。希望の値、提出済み状態、公開後カレンダー、監査ログが一致せず、勤怠・月次ツールもない。この状態ではMCP経由の操作を正式運用に含めにくい。

## 主要な業務リスク

1. 一般メンバーが管理者の評価メモを閲覧できる。
2. 同一人物の同時打刻で複数の勤務が開始される。
3. 未来日の割当へ打刻でき、日次未提出でも月次承認できる。
4. 管理者2人のシフト編集が警告なしで上書きされる。
5. MCP操作後の状態がBrowser/APIと一致しない。
6. 100人シフト割当が24,800個のチェックボックス、100人管理が17,340pxの一覧となり、日常操作が難しい。

## 規模試験

| 条件 | 結果 |
|---|---|
| 10グループ | 一覧取得成功。操作欄が全展開され、初期取得もグループ数に比例 |
| 1グループ100人 | API取得成功。管理画面は検索・ページ分割なし |
| 31日・248枠・496割当 | API取得成功。画面は24,800チェックボックスを描画 |
| 50人同時グループ取得 | 50/50成功、p95 3.01秒 |
| 50人同時希望保存 | 50/50成功、p95 2.53秒 |
| 50人同時出勤 | 50/50成功、p95 3.16秒 |
| 同一人20件同時出勤 | 19件の勤務レコードが作成され不合格 |
| 100人×12か月×月4件 | 4,800件。最大応答3.63MB、最大1.90秒 |

ローカル単体プロセスの数値であり、本番性能の保証値ではない。ただしデータ一括返却と巨大DOMは環境を速くしても残る構造的な問題である。

## Browserで確認したこと

- 空の状態からグループを作成でき、成功表示された。
- シフト作成、月次集計、10グループ一覧、100人管理、100人シフト割当を実画面で確認した。
- 主要画面でブラウザーコンソールエラーはなかった。
- 月次の負数時間表示と、大規模一覧の操作性に問題があった。
